## ⚠️ Critical: spec/collection divergence — read before writing API code

The Postman collection does **not** describe the product the BRD and spec define. It reads like a generic multi-tenant legal-SaaS boilerplate: it has public self-signup (`POST /auth/signup` with `userType`/`firmName`), a public lawyer marketplace (`/public/lawyers`), client reviews (`/reviews`), consultation booking (`/consultations`), hard `DELETE` on cases/documents/invoices/payments/courts/users, and a `tenantId` field the client supplies directly in request bodies. Every one of those either contradicts a specific BR-### rule or something the BRD explicitly lists as out-of-scope. Full itemized list in `API_CONTRACT.md` → "Gap Analysis Summary."

There's also **no subscription/billing surface at all** in the collection — no plan, no status field, no `X-Subscription-Status` header anywhere. BR-010/012's read-only-mode mechanism (which the spec's whole `ReadOnlyGuard` is built around) has no data source to read from in this API. Same for MFA (BR-033/6.1.3 says mandatory for Firm Admin — no `/auth/mfa/verify` exists) and case timeline (BR-017 — no `GET /cases/{id}/timeline`).

**⚠️ The subscription gap above is stale as of 2026-08-05 — this paragraph describes the Postman collection only, not the current backend.** A real `subscriptions` module now exists server-side, enforced by a global `SubscriptionGuard` that's stricter than the `ReadOnlyGuard` degrade this paragraph assumed — see the BR-010 row above and API_CONTRACT.md finding M. MFA and case-timeline are still genuinely absent, unchanged.

**Decision (confirmed 2026-07-30): treat the collection as literal ground truth.** Build the `dio` client and repositories against exactly what's callable today. This does NOT mean wiring every endpoint blindly — still flag a BR conflict inline the moment a milestone would use it (e.g. don't wire a destructive UI action to `DELETE /cases/{id}` without asking first), but don't block work waiting for a backend fix.

## Non-negotiable rules (BR-###)

| ID | Rule | App must do |
|---|---|---|
| BR-003 | Tenant isolation, row-scoped | Never send `tenant_id`/`tenantId` from the client (backend derives it from the JWT). `TenantInterceptor`'s client-side header injection was removed in M1 for this reason. **`POST /users` does NOT override a client-supplied `tenantId` server-side (confirmed 2026-08-06, `API_CONTRACT.md` finding AA) — unlike Cases, the Flutter app itself must inject the current session's `tenantId` into every create call, the same `ClientRepository`-style pattern, except here it's load-bearing, not just defensive.** Cross-tenant fetch → 404 rendered as "Not found," never "Forbidden." **Critical, separate issue confirmed the same day (`API_CONTRACT.md` finding Z): `GET /users` has zero tenant filtering server-side — it returns every user account on the entire platform, not just the caller's own tenant.** This affects code shipped since M4 (`UserRepository`'s use as Case/Task assignee-picker reference data) — every `GET /users` response must be filtered client-side to `user.tenant?.id == current tenantId` before use, retroactively as well as in any new M7 screen. |
| BR-005 | Firm Admin full CRUD, non-restrictable | Never hide a module from Firm Admin in UI gating. **Firm Admin detection changed 2026-08-05 (API_CONTRACT.md finding L):** a real `FIRM_ADMIN` role now exists and is what the backend itself checks (`roles.includes('FIRM_ADMIN')` in every server-side authorization check) — confirmed directly by the backend team. The `Tenant.ownerUserId == user.id` mechanism this app used since M2 is **obsolete, do not use it going forward**; `isFirmAdmin` is now `User.roles.any((r) => r.code == 'FIRM_ADMIN')`, a synchronous getter on the already-fetched user, no separate network call. |
| BR-010 | Subscription lifecycle → read-only mode | **Superseded 2026-08-05 (API_CONTRACT.md finding M) — the "read-only mode with a banner" UX this row originally described does not match real backend behavior and should not be built.** A global `SubscriptionGuard` blocks *every* authenticated request (reads included, not just writes) with `402 Payment Required` whenever the tenant's subscription isn't `ACTIVE` and unexpired — confirmed intentional by the backend team, not a bug to work around. The app's actual behavior: catch 402 anywhere via `mapDioError()` → `SubscriptionInactiveFailure`, transition to a dedicated app-wide blocking screen (not a banner — reads are blocked too, so a degraded-but-usable UI isn't possible), with a self-service "Reactivate" action (`POST /subscriptions/activate`) shown to `FIRM_ADMIN` users only. |
| BR-016/BR-024/BR-028/BR-029 | No hard delete (cases, documents, financial records) | **Confirmed satisfied for cases/clients/documents/tenants/calendar-events/courts/opponents/users** (2026-07-30 re-sync + 2026-08-06 re-confirmation): all use TypeORM soft-delete (`@DeleteDateColumn`/`isArchived` via `.softRemove()` — see `API_CONTRACT.md` finding C). **Violated for financial records specifically, found 2026-08-06 (`API_CONTRACT.md` finding R):** `FinanceService.removeInvoice`/`.removePayment` both call `.remove()` — a real hard delete on invoices and payments, the exact entities BR-028/BR-029 name. This line previously (wrongly) claimed Finance was covered by the general soft-delete pattern; that was never checked against Finance source until this pass. No Flutter delete UI exists for Finance yet, so nothing is retroactively broken — but **do not wire one without a business-rule conversation first.** `hearings`/`tasks` also hard-delete (`API_CONTRACT.md` finding I) but aren't named in these BR numbers, so that inconsistency is noted, not a violation. |
| BR-026 | Case-fee visibility restricted to Firm Admin / `finance.read` | **Fixed 2026-07-30, mechanism updated 2026-08-05:** `agreedFee` on `LegalCase` is hidden unless `SessionCubit`'s authenticated user reports `isFirmAdmin`. Originally computed via `Tenant.ownerUserId == user.id` (API_CONTRACT.md finding D, now obsolete — see BR-005 row); now computed via the real `FIRM_ADMIN` role code (finding L). Apply the same hide-by-default pattern (default `false` on any failure/ambiguity) to any other finance-gated field. |
| BR-030 | Per-firm isolated RAG | AI chat renders only `sources[]` the backend returns; never merge/cache across tenants. |
| BR-032 | AI is advisory | Every AI output shows "AI-generated — verify before use"; human edits always win over AI output. |
| BR-033 | Auth | Access token short-lived, in memory only; refresh token in `flutter_secure_storage` only, never plain SharedPreferences/Hive. |
| BR-034 | RBAC enforced at backend | UI hides disallowed actions as UX only; always handle a 403 gracefully — never assume UI gating is sufficient. |
| BR-037 | Mobile/API parity | This app is a client of the same tenant-scoped API as web. No mobile-only shortcut endpoints. |

Full rule set: BRD §7 (BR-001 – BR-037). Ask before writing code that could violate one.

**Push notifications:** deferred to M6 per spec — no Firebase project wiring before then.

## Coding conventions

- All HTTP calls go through a single `dio` client configured per `API_CONTRACT.md` — no endpoint strings hardcoded inside feature repositories.
- Every user-facing string localized from day one. New strings go in ARB (`lib/l10n/`); existing screens' strings stay in `assets/lang/*.json` until their own migration milestone — don't mix the two within one new screen.
- Test every screen in EN LTR and AR RTL.
- API repository tests mock `dio` (via `mocktail`) and assert request shape matches `API_CONTRACT.md` exactly (method, path, body keys/casing).
- Freezed for all DTOs; camelCase JSON keys per the actual collection (not the snake_case the spec guessed).
- Commit in small, milestone-scoped chunks referencing the milestone + BR-### or endpoint touched.
- Widget tests: avoid `pumpAndSettle()` when the tree contains an indeterminate `CircularProgressIndicator` (never settles → timeout) or a `SnackBar` (its ~4s auto-dismiss timer gets fast-forwarded past, so the assertion finds nothing) — use a couple of fixed-duration `pump()` calls instead. If a widget test needs the real JSON-based `AppLocalizations` and lives in a file with multiple `testWidgets` blocks, preload it once in `setUpAll` and serve it via a `SynchronousFuture`-based delegate rather than letting each test await the real `rootBundle` load — that async gap doesn't reliably resolve past the first `pumpWidget` in one file (see `login_page_test.dart`).

    - **Critical, affects code already shipped:** `GET /users` has zero tenant scoping at the query level (`UserRepository.findAll()` has no `where` clause at all) — it returns every user account on the entire platform, not just the caller's tenant. This app has called this endpoint since M4 without knowing it leaks cross-tenant PII. Fixed the BR-003 table row above; the required client-side mitigation (filter every response to `user.tenant?.id == current tenantId`) applies retroactively to the existing Case/Task assignee pickers, not just any new M7 screen — this is the first action item M7 needs to take, before anything else.
    - Two more real gaps: `POST /users` doesn't override a client-supplied `tenantId` server-side (unlike Cases) — the Flutter app must inject it itself, load-bearing this time, not just defensive; and `PATCH /users/{id}` silently discards `roleIds` (the service deletes the key from the update payload before persisting) — role reassignment after creation doesn't work through any reachable endpoint (the Employees-module route collision, re-confirmed still present, doesn't offer an alternate path either).
    - Two independent privilege-escalation surfaces to close off client-side, not trust the backend to have closed: `GET /roles`'s own exclusion filter checks for the string `'SYSTEM_ADMIN'`, but the seeded platform role is actually `'SUPER_ADMIN'` — a different string — so `SUPER_ADMIN` is returned by the endpoint and would appear in a naive role-picker; and `CreateUserDto.isSuperAdmin` is a plain client-settable boolean with no server-side restriction on who can set it `true`.
    - `DELETE /users/{id}` is a hard delete, but — unlike the Hearings/Tasks inconsistency — a deliberate one: the code comments explain a soft-deleted row would permanently block that email address from reuse, given the column's plain `UNIQUE` constraint. Recommended using `PATCH status: SUSPENDED|DEACTIVATED` as the "remove a staff member" action instead of wiring the DELETE endpoint, matching the "deactivate, don't delete" pattern already used for Courts (BR-021) — a recommendation, not a hard blocker, since the reasoning here is different in kind from Hearings/Tasks.
